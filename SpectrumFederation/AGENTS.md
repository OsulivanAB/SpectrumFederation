# SpectrumFederation – Agent Notes (Addon Code)

These notes apply when changing files under `SpectrumFederation/`.

## Branch policy reminder
- Copilot PRs must target `beta` (work branches start from `beta`).
- `main` is release-only.

## Scope control (prevent creep)
- Keep PRs **small and targeted**. Do not refactor unrelated systems “while you’re here.”
- Do not add new third‑party libraries unless explicitly requested.
- Prefer extending existing patterns over inventing new frameworks.
- Inspect existing architecture, callers, lifecycle, and persisted data before assuming a change is local, safe, or complete.

## Change contract for technically risky work

When a change introduces or materially alters shared/persisted state, caches or
derived state, queues, retries, reservations, deferred work, asynchronous side
effects, cross-client sync/protocol semantics, shared UI infrastructure, or
recurring runtime work, briefly establish authority, guarantee, dependencies,
lifecycle, and evidence before building the machinery. A few sentences in the
task context is normally enough. Ordinary local fixes do not need a design
document. Reuse and update an existing repair contract rather than redesigning
the feature. Do not treat a local flag, timeout, or successful API call as
proof of a stronger cross-client guarantee than the evidence supports. Escalate
architecture or product trade-offs instead of silently weakening the
requirement. Repo-wide framing: root `AGENTS.md`.

## Client Stability (Highest Runtime Priority)

Preventing World of Warcraft client crashes, freezes, severe UI hangs, runaway execution, and long-session performance degradation is one of the highest priorities whenever reviewing, auditing, designing, or modifying SpectrumFederation.

This is an engineering requirement, not a generic reminder to “consider performance.” It does not replace inspect-before-assuming, architecture-first changes, compatibility, functionality preservation, performance awareness, appropriate testing, or minimal targeted edits.

Addon Lua executes primarily on the game’s UI thread. A problem does **not** need to be literally infinite to be dangerous. For example:

```text
event
→ expensive rebuild
→ event
→ expensive rebuild
```

or:

```text
resize
→ reflow
→ resize
→ reflow
```

or:

```text
every frame
→ scan/rebuild many objects
```

can make the client appear frozen even if execution eventually yields.

### Risks to consider

When reviewing, auditing, designing, or changing runtime addon code, actively consider whether the change could create or worsen:

- synchronous infinite or effectively unbounded loops
- callback recursion or re-entrancy
- UI layout/reflow feedback loops
- `OnSizeChanged` → layout → `OnSizeChanged` cycles
- `OnShow` / `OnHide` lifecycle feedback
- event → state mutation → same-event feedback
- high-frequency `OnUpdate` work
- timers/tickers that continue after their feature becomes inactive
- self-scheduling timer loops
- duplicate callbacks/listeners after repeated page opens
- addon-message request/response or rebroadcast storms
- queues that can fail to drain
- inspect/item-data retry storms
- full-database or full-UI rebuilds triggered at high frequency
- continuously growing frame/texture/animation allocations
- long-session resource accumulation
- large synchronous SavedVariables/profile/history processing
- expensive work on login/reload
- errors hidden behind `pcall` or other mechanisms that make crashes/freezes difficult to diagnose

### Idle means idle

When a SpectrumFederation feature has no state change, no user interaction, and no intentionally scheduled task to perform, it should generally become idle.

A UI page merely remaining visible should not continuously rebuild itself, reflow itself, inspect players, reconstruct databases, schedule refreshes, allocate objects, or broadcast synchronization traffic.

Exceptions should have an intentional and documented reason.

### Repeated lifecycle operations must remain bounded

Repeated operations such as `open → close → open → close`, `enable → disable → enable`, `show page A → page B → page A`, or repeated window resizing must not continually accumulate listeners, callbacks, timers, tickers, frames, textures, pending deferred callbacks, inspect requests, or synchronization work.

Where practical, reviews and tests should verify that resource counts **converge rather than grow with repetition**.

### Queues and deferred work must converge

For queues, retries, debounces, and deferred work, the expected lifecycle should generally be:

```text
producer stops
→ queued work drains
→ queue becomes empty
→ processor/ticker becomes idle
```

Investigate any system where new work can be generated by processing old work.

### Cache correctness

For a new or changed cache, establish:

- the authoritative inputs and cache scope;
- every relevant invalidation path;
- handling of incomplete or stale data;
- reset, lifecycle, and ownership behavior;
- tests for both reuse and reevaluation.

Prefer appropriately scoped invalidation. Global invalidation is acceptable when
the dependency is genuinely global; do not invalidate unrelated results merely
because a shared UI version changed. Unknown or incomplete data must not become
authoritative solely because a fallback, retry, or timeout was used.

### Retry and deferred-work correctness

Bound cadence, concurrent work, memory, and lifecycle.

Do not silently abandon a required unfinished obligation merely to impose a
fixed retry count. Define whether exhaustion means explicit failure, backoff,
retained pending state, cancellation, or an owner-visible decision.
Conversely, do not retry forever without a valid remaining obligation and
lifecycle boundary.

Treat expiry, cancellation, successful completion, and uncertain delivery as
different states where the contract requires it. A timeout alone does not prove
that an external side effect did not happen. When deferring work, preserve
freshness, authority checks, and ordering.

### Performance evidence

Support performance findings and optimizations with a clear mechanism,
proportionate cost analysis, or focused measurement. Consider work per event,
event frequency, roster/history size, allocation growth, and idle behavior.
Distinguish measured results from estimates.

An obvious runaway path does not require a benchmark before being fixed.
Ordinary repeated work is not automatically a demonstrated freeze. Use batching,
coalescing, caching, or incremental processing when justified. Do not add complex
optimization machinery or permanent hot-path instrumentation without a
demonstrated need.

### Shared UI infrastructure requires extra care

Shared Settings/UI infrastructure deserves elevated scrutiny. Changes to `Section`, `PageBuilder`, shared Controls, ScrollFrames, sizing/layout helpers, or shared refresh mechanisms can affect many addon pages.

When changing these systems, look for re-entrancy and feedback loops and inspect major consumers before declaring the change safe.

### Testing expectations

When modifying code involving UI layout, sizing, callbacks, events, timers, tickers, listeners, queues, inspection, synchronization, or repeated refreshes, strongly prefer regression tests that verify **bounded execution and convergence**, rather than merely verifying that no Lua error occurred.

Examples of useful assertions:

- refresh count stops increasing once stable
- listener count does not increase after 100 open/close cycles
- same-size resize events produce no continuing work
- queue eventually reaches zero
- disable leaves no active ticker
- idle time advancement produces no additional refreshes

Do not require artificial counters everywhere; use judgment and the existing testing infrastructure. The principle is what matters.

Existing Lua 5.1 suites already cover several of these areas (`tests/test_raid_equipment.py`, `tests/test_settings_window_layout.py`, `tests/test_mouse_tracer.py`). Extend those suites when the touched code already has tests.

### Behavioral regression evidence

For stateful or cross-component fixes, test the relevant sequence of events and
observable outcome, not only isolated helpers or source structure. Prefer the
existing production-Lua and Python infrastructure. Mock external boundaries
without bypassing the production decision or transition under test.

Examples of intended evidence:

- a cache skips unchanged work but reevaluates after every relevant dependency changes;
- removing one consumer cancels work no longer required without disabling another consumer's valid work;
- a failed side effect releases or preserves the correct owner's pending state according to the contract;
- reload restores both durable state and any unfinished obligation;
- an exception leaves cleanup and future scheduling in the intended state;
- delayed or duplicate messages do not create duplicate authoritative effects.

Source-text checks remain useful for structural requirements such as load order
or forbidden API usage. However:

- the presence of a function name or comment is not evidence that its runtime behavior is correct;
- source-order assertions and helper unit tests alone do not establish a cross-component lifecycle guarantee;
- passing assertion counts are not a substitute for relevant coverage.

For regression repairs, when practical in the authorized test environment,
demonstrate that the regression test fails against the broken behavior and
passes after the fix. Confirm the failure is behavioral, not merely a missing
symbol or broken test setup. Do not weaken the expectation just to obtain a
pass. When that demonstration is impractical, state the limitation and the
evidence actually obtained. A trustworthy code trace is useful; it must not be
described as an executed test.

Choose representative, risk-based event sequences. Do not demand exhaustive
permutations, a new simulator for every feature, or every suite after every
edit. This execution guidance applies to authorized implementation/validation
and to owner-requested assessment only when that request includes execution.

### Reviews and audits

When asked to perform a code review, technical audit, pre-release review, or architecture review, client stability is one of the **top review dimensions by default** whenever runtime addon behavior is involved, even if the prompt does not mention crashes.

Check relevant code for plausible freeze/crash mechanisms. Avoid false positives. Do **not** report every loop, timer, `OnUpdate`, event handler, or large function as dangerous merely because it exists. Trace actual callers, lifecycle, bounds, and termination conditions. The goal is to find **credible failure mechanisms**, not to generate a long scary checklist.

### Observability and error recovery

When handling unexpected programming errors, avoid accidentally making severe runtime defects invisible.

Protected execution such as `pcall` can be appropriate for cleanup and resilience, but unexpected errors should generally remain observable through WoW’s normal error handler / BugGrabber where practical.

Do not turn expected runtime conditions into fatal errors merely for observability. Expected debug logging should still stay off hot paths.

Protect cleanup, re-entrancy guards, and scheduling where appropriate while
preserving unexpected-error visibility. Neither swallowing errors nor
rethrowing before required cleanup is a complete recovery strategy.

## WoW Lua constraints (hard rules)
- Lua runtime is **Lua 5.1** (WoW embedded). Avoid 5.2+ syntax/features.
- No `io`, `os`, filesystem access, sockets, or external processes (WoW sandbox).
- Avoid UI taint and protected frame issues:
  - Prefer `hooksecurefunc` over overwriting Blizzard functions.
  - Avoid modifying protected UI in combat; guard with `InCombatLockdown()` when relevant.

## Adding a new setting (correct, minimal workflow)
When you need a new toggle/option:
1. **Schema:** add the setting definition to `modules/Settings/Schema.lua`.
   - Use a stable key name (prefer `snake_case`).
   - Add a default value.
   - Place it under the appropriate section (e.g., **General**).
2. **Storage:** follow existing patterns in `modules/Settings/Store.lua` (many settings are automatic—copy what existing settings do).
3. **Apply behavior:** ensure the setting actually affects runtime behavior.
   - Prefer handling in the feature module, but use `modules/Settings/Apply.lua` if that’s the established pattern.
4. **UI:** render it in the Settings UI (typically `modules/UI/Settings/Pages/General.lua` for General).
   - Use the existing renderer, registry, and standalone window—do not create a second UI system.
   - New pages use `categoryId` for the sidebar category. Legacy `parentId` still works. Categories with two or more content pages appear as tabs, not nested sidebar rows.
5. **Schema migrations:** avoid unless strictly necessary. If needed, keep it tiny and backward-compatible.

## Debug logging (required for new features)
- Use `SF.Debug` for diagnostic output.
- Prefer existing call patterns:
  - Search for existing `SF.Debug:` call sites and mirror the signature.
  - The debug module supports a core `Log(level, category, message, ...)` style; wrapper helpers may exist (e.g., `Info/Warn/Error/Verbose`) — reuse what the codebase already uses.
- Log:
  - User-triggered actions and feature start/stop (INFO)
  - Recoverable problems (WARN)
  - Unexpected nils / failed API calls / hard failures (ERROR)
- Do not log in hot paths (tight loops, per-frame handlers).

## User-visible messaging

User-facing chat output is opt-in.
Do not add new output to normal WoW chat unless:
1. The task/issue explicitly asks for that message or behavior to be shown in chat; or
2. The user has explicitly approved adding it.
Do not infer permission because a message seems useful, actionable, important, or error-related.
If an implementation would benefit from new chat output but the request does not authorize it, ask the user before adding it. If interactive clarification is not possible, do not add the chat output; note the proposed message for the user instead.
If the information is useful for diagnostics, troubleshooting, or development, use `SF.Debug` rather than normal chat. If it has no diagnostic value, it does not need replacement output at all.

When chat output *is* authorized, prefer `modules/MessageHelpers.lua` helpers (`SF:PrintSuccess/Error/Warning/Info`, `SF:SystemMessage`) over ad-hoc `print` / `DEFAULT_CHAT_FRAME:AddMessage`. Do not spam chat for debugging.

### Anti-spam and repetition (proactive requirement)

When adding or reviewing **any user-visible output** — chat messages, warnings, notifications, alerts, UI banners/toasts, errors from addon communications, status messages — proactively evaluate repetition/spam risk during **design, implementation, and review**, even if the task did not mention spam prevention.

**Key question:** Can the same underlying condition cause this message to be emitted repeatedly without anything meaningful having changed?

Pay particular attention when output is reachable from recurring execution: heartbeats, timers, `OnUpdate`, polling, retries, synchronization, addon communications, recurring callbacks, frequently firing game events, state refreshes, reconnect/recovery logic, and repeated validation or compatibility checks.

**Choose protection appropriate to the behavior** (not an arbitrary cooldown on every message):

- **State-transition messaging:** notify when a condition *becomes* true, not every time it is observed. Example: compatible → incompatible warns once; subsequent heartbeats while still incompatible stay silent; if compatibility is restored and later breaks again, a new warning is appropriate.
- **Deduplication:** suppress identical repeats until something meaningful changes. Key by relevant context (player, warning type, protocol/version, item, feature, session, etc.). Do not deduplicate globally when separate occurrences genuinely matter.
- **Meaningful-change detection:** if repeated processing discovers no new information, do not re-inform the user.
- **Rate limiting:** use when repeated reminders are useful but should not fire at the underlying event frequency. Prefer state/dedup design first.

Recurring processing (heartbeats, sync ticks, retries) should continue as needed. Suppress **redundant user-visible output**, not necessary processing.

**This does not mean:** hide useful errors, eliminate warnings, make failures silent, suppress genuinely new information, apply long cooldowns to everything, or remove diagnostic logging for development. Distinguish `SF.Debug` diagnostics from normal user-facing output.

**Review checklist** (treat obvious uncontrolled spam paths as implementation-quality issues):

1. What causes the message?
2. How often can that code path execute?
3. Can the triggering condition remain true across multiple executions?
4. Would those executions produce substantially identical messages?
5. What constitutes a genuinely new occurrence?
6. Does the design already include state, deduplication, edge detection, aggregation, or rate limiting?
7. Could failure/retry behavior accidentally multiply the output?

For sync/comm warning deduplication patterns, see `tests/test_sync_protocol.py` and existing Loot Helper sync code.

## Localization (mandatory pre-delivery check)

Canonical policy for packaged addon user-facing text. Other instruction files
should reference this section rather than restating a weaker version.

Before declaring packaged addon work complete, explicitly audit every **new or
modified** user-facing string introduced by the change—not only Settings pages:

- Labels, button text, status/empty states, tooltips, warnings, errors, and
  other player-visible copy in Lua/UI modules
- Route those strings through the established localization system:
  `locale/enUS.lua` + `ns.L` / `SF.L`, typically via `SF.LocaleText(key, default)`
- Verify `locale/enUS.lua` (and any new locale file) is listed in the owning
  addon's TOC **before** modules that render those strings
- Prefer stable locale keys; keep English defaults as fallbacks so tests and
  incomplete locale tables remain usable
- Internal identifiers, protocol field names, debug/diagnostic output, and
  other non-user-facing strings do **not** require localization
- Do **not** expand a task into a wholesale migration of unrelated legacy
  hardcoded strings unless the owner explicitly asks for that migration
- The PR checklist item for `locale/enUS.lua` may be checked only after this
  audit against the actual diff. Do not check it automatically, assume it is
  satisfied, or treat localization as optional follow-up for automated review

Localization compliance is part of implementation completion for packaged
addon changes.

## Packaging + versioning
- **Any new Lua file must be listed in** the TOC of the addon that owns it (`SpectrumFederation.toc` or the owning child-addon TOC).
- Parent TOC files must not load child-addon Lua or XML.
- Packaged behavior/UI/settings/runtime changes must bump `## Version:` in
  `SpectrumFederation/SpectrumFederation.toc` and keep packaged child TOCs on
  the same Version and Interface values. Deterministic
  `release_required` classification owns when a bump is mandatory; zip-excluded
  guidance files (including this `AGENTS.md`) are not packaged releases. A
  repair iteration does not automatically require another increment when the
  PR version is already valid and ahead of the base. Full policy: root
  `AGENTS.md` Packaging And Versioning.
