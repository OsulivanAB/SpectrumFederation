# SpectrumFederation – Agent Notes (Addon Code)

These notes apply when changing files under `SpectrumFederation/`.

## Branch policy reminder
- Copilot PRs must target `beta` (work branches start from `beta`).
- `main` is release-only.

## Scope control (prevent creep)
- Keep PRs **small and targeted**. Do not refactor unrelated systems “while you’re here.”
- Do not add new third‑party libraries unless explicitly requested.
- Prefer extending existing patterns over inventing new frameworks.
- Inspect existing architecture, callers, lifecycle, and persisted data before assuming a change is local, safe, or complete.

## Client Stability (Highest Runtime Priority)

Preventing World of Warcraft client crashes, freezes, severe UI hangs, runaway execution, and long-session performance degradation is one of the highest priorities whenever reviewing, auditing, designing, or modifying SpectrumFederation.

This is an engineering requirement, not a generic reminder to “consider performance.” It does not replace inspect-before-assuming, architecture-first changes, compatibility, functionality preservation, performance awareness, appropriate testing, or minimal targeted edits.

Addon Lua executes primarily on the game’s UI thread. A problem does **not** need to be literally infinite to be dangerous. For example:

```text
event
→ expensive rebuild
→ event
→ expensive rebuild
```

or:

```text
resize
→ reflow
→ resize
→ reflow
```

or:

```text
every frame
→ scan/rebuild many objects
```

can make the client appear frozen even if execution eventually yields.

### Risks to consider

When reviewing, auditing, designing, or changing runtime addon code, actively consider whether the change could create or worsen:

- synchronous infinite or effectively unbounded loops
- callback recursion or re-entrancy
- UI layout/reflow feedback loops
- `OnSizeChanged` → layout → `OnSizeChanged` cycles
- `OnShow` / `OnHide` lifecycle feedback
- event → state mutation → same-event feedback
- high-frequency `OnUpdate` work
- timers/tickers that continue after their feature becomes inactive
- self-scheduling timer loops
- duplicate callbacks/listeners after repeated page opens
- addon-message request/response or rebroadcast storms
- queues that can fail to drain
- inspect/item-data retry storms
- full-database or full-UI rebuilds triggered at high frequency
- continuously growing frame/texture/animation allocations
- long-session resource accumulation
- large synchronous SavedVariables/profile/history processing
- expensive work on login/reload
- errors hidden behind `pcall` or other mechanisms that make crashes/freezes difficult to diagnose

### Idle means idle

When a SpectrumFederation feature has no state change, no user interaction, and no intentionally scheduled task to perform, it should generally become idle.

A UI page merely remaining visible should not continuously rebuild itself, reflow itself, inspect players, reconstruct databases, schedule refreshes, allocate objects, or broadcast synchronization traffic.

Exceptions should have an intentional and documented reason.

### Repeated lifecycle operations must remain bounded

Repeated operations such as `open → close → open → close`, `enable → disable → enable`, `show page A → page B → page A`, or repeated window resizing must not continually accumulate listeners, callbacks, timers, tickers, frames, textures, pending deferred callbacks, inspect requests, or synchronization work.

Where practical, reviews and tests should verify that resource counts **converge rather than grow with repetition**.

### Queues and deferred work must converge

For queues, retries, debounces, and deferred work, the expected lifecycle should generally be:

```text
producer stops
→ queued work drains
→ queue becomes empty
→ processor/ticker becomes idle
```

Investigate any system where new work can be generated by processing old work.

### Shared UI infrastructure requires extra care

Shared Settings/UI infrastructure deserves elevated scrutiny. Changes to `Section`, `PageBuilder`, shared Controls, ScrollFrames, sizing/layout helpers, or shared refresh mechanisms can affect many addon pages.

When changing these systems, look for re-entrancy and feedback loops and inspect major consumers before declaring the change safe.

### Testing expectations

When modifying code involving UI layout, sizing, callbacks, events, timers, tickers, listeners, queues, inspection, synchronization, or repeated refreshes, strongly prefer regression tests that verify **bounded execution and convergence**, rather than merely verifying that no Lua error occurred.

Examples of useful assertions:

- refresh count stops increasing once stable
- listener count does not increase after 100 open/close cycles
- same-size resize events produce no continuing work
- queue eventually reaches zero
- disable leaves no active ticker
- idle time advancement produces no additional refreshes

Do not require artificial counters everywhere; use judgment and the existing testing infrastructure. The principle is what matters.

Existing Lua 5.1 suites already cover several of these areas (`tests/test_raid_equipment.py`, `tests/test_settings_window_layout.py`, `tests/test_mouse_tracer.py`). Extend those suites when the touched code already has tests.

### Reviews and audits

When asked to perform a code review, technical audit, pre-release review, or architecture review, client stability is one of the **top review dimensions by default** whenever runtime addon behavior is involved, even if the prompt does not mention crashes.

Check relevant code for plausible freeze/crash mechanisms. Avoid false positives. Do **not** report every loop, timer, `OnUpdate`, event handler, or large function as dangerous merely because it exists. Trace actual callers, lifecycle, bounds, and termination conditions. The goal is to find **credible failure mechanisms**, not to generate a long scary checklist.

### Observability

When handling unexpected programming errors, avoid accidentally making severe runtime defects invisible.

Protected execution such as `pcall` can be appropriate for cleanup and resilience, but unexpected errors should generally remain observable through WoW’s normal error handler / BugGrabber where practical.

Do not turn expected runtime conditions into fatal errors merely for observability. Expected debug logging should still stay off hot paths.

## WoW Lua constraints (hard rules)
- Lua runtime is **Lua 5.1** (WoW embedded). Avoid 5.2+ syntax/features.
- No `io`, `os`, filesystem access, sockets, or external processes (WoW sandbox).
- Avoid UI taint and protected frame issues:
  - Prefer `hooksecurefunc` over overwriting Blizzard functions.
  - Avoid modifying protected UI in combat; guard with `InCombatLockdown()` when relevant.

## Where to put code
- Entry point / initialization / events: `SpectrumFederation/SpectrumFederation.lua`
- Core helpers (time/version/etc): `SpectrumFederation/modules/Core.lua`
- Player/name normalization: `SpectrumFederation/modules/NameUtil.lua`
- User messages: `SpectrumFederation/modules/MessageHelpers.lua`
- Debug logger: `SpectrumFederation/modules/debug.lua` (`SF.Debug`)
- Settings:
  - Schema/Store/Apply: `SpectrumFederation/modules/Settings/`
  - Settings UI framework + pages: `SpectrumFederation/modules/UI/Settings/`
- Mouse Tracer: `SpectrumFederation/modules/MouseTracer/` (constants, pure trail engine, runtime host). The Gameplay / UI Enhancements page lives in `modules/UI/Settings/Pages/NicheFeatures.lua`.

## Adding a new setting (correct, minimal workflow)
When you need a new toggle/option:
1. **Schema:** add the setting definition to `modules/Settings/Schema.lua`.
   - Use a stable key name (prefer `snake_case`).
   - Add a default value.
   - Place it under the appropriate section (e.g., **General**).
2. **Storage:** follow existing patterns in `modules/Settings/Store.lua` (many settings are automatic—copy what existing settings do).
3. **Apply behavior:** ensure the setting actually affects runtime behavior.
   - Prefer handling in the feature module, but use `modules/Settings/Apply.lua` if that’s the established pattern.
4. **UI:** render it in the Settings UI (typically `modules/UI/Settings/Pages/General.lua` for General).
   - Use the existing renderer, registry, and standalone window—do not create a second UI system.
   - New pages use `categoryId` for the sidebar category. Legacy `parentId` still works. Categories with two or more content pages appear as tabs, not nested sidebar rows.
5. **Schema migrations:** avoid unless strictly necessary. If needed, keep it tiny and backward-compatible.

## Debug logging (required for new features)
- Use `SF.Debug` for diagnostic output.
- Prefer existing call patterns:
  - Search for existing `SF.Debug:` call sites and mirror the signature.
  - The debug module supports a core `Log(level, category, message, ...)` style; wrapper helpers may exist (e.g., `Info/Warn/Error/Verbose`) — reuse what the codebase already uses.
- Log:
  - User-triggered actions and feature start/stop (INFO)
  - Recoverable problems (WARN)
  - Unexpected nils / failed API calls / hard failures (ERROR)
- Do not log in hot paths (tight loops, per-frame handlers).

## User-visible messaging
- Prefer `modules/MessageHelpers.lua` helpers (`SF:PrintSuccess/Error/Warning/Info`) when you need to tell the user something.
- Do not spam chat for debugging (use `SF.Debug` instead).

## Localization
- If the repo has `locale/enUS.lua` and `ns.L`, use it for new user-facing strings.
- If existing code is not fully localized yet, keep your additions consistent with the existing direction (don’t introduce a third pattern).

## Packaging + versioning
- **Any new Lua file must be listed in** the TOC of the addon that owns it (`SpectrumFederation.toc` or the owning child-addon TOC).
- Parent TOC files must not load child-addon Lua or XML.
- **Any behavior/UI/settings change must bump** `## Version:` in `SpectrumFederation/SpectrumFederation.toc` and keep packaged child TOCs on the same version.

## Validation checklist (do these before declaring “done”)
- `python3 .github/scripts/lint_all.py`
- For layout, sizing, callback, event, timer, listener, queue, inspect, or sync changes: prefer tests that assert bounded execution and convergence, using the existing Lua 5.1 suites below.
- `/reload` in-game without errors.
- Verify the new setting appears (when applicable) and toggling it changes behavior as intended.
- Settings navigation changes: `python -m pytest tests/test_settings_navigation.py`
- Settings window content layout / impersonation banner: `python -m pytest tests/test_settings_window_layout.py`
- Mouse Tracer engine or constants changes: `python -m pytest tests/test_mouse_tracer.py`
- Raid Equipment policy, CheckRun, or Raid Check lifecycle changes: `python -m pytest tests/test_raid_equipment.py`
- Loot Helper impersonation / Preview as Non-Admin: `python -m pytest tests/test_impersonation.py`
- Linked character identities: `python -m pytest tests/test_linked_identity.py`
- Sync protocol NACK/warning throttling: `python -m pytest tests/test_sync_protocol.py`
- RC Loot Council Integration child addon: `python -m pytest tests/test_rc_loot_council_integration.py`
