## Guarantees

1. Reads/startup never create per-guild records; `CreateStagedRecord` is explicit. No legacy Consumables import.
2. Durable key is only `club:<actual id>`; `name:` transport scopes are rejected.
3. Default editor threshold is logical rank position 3; labels use actual rank names.
4. Invalid/out-of-range policy permits verified Guild Master recovery only.
5. Compare-and-apply statuses: accepted / duplicate / pending / rejected.
6. Missing data fails closed; commit/admission rechecks guild/rank/policy.
7. Chat-free: enabled `SF.Debug` only. Settings banners use `FormatMutationFeedback`.
8. **3C:** Any verified authorized editor (not GM-only) may activate. Activation requires a fresh bank sample on the activating client, publishes a durable cutover marker, and is idempotent.
9. **3C:** Pre-activation bank rows / staged pending evidence / staged accepted ledger rows never become live credit (`gsProductionCredit`). Compatible peers adopt cutover without reopening the bank. Authenticated divergent live markers fail closed on production writers.
10. **3C:** After activation, `ShouldUseLegacyConsumablesWriters()` is false; profile ApplyOp/CommitEvents/MergeSnapshot and legacy sync handlers cannot mutate production accounting for that guild.
11. **3C:** Staged sample-only bank observation lets an authorized editor stamp the configured GS tab without admitting donations or requiring a legacy profile. Remote live cutover install requires verified editor authority.
12. **3B / #411:** A current officer's new local completed Guild Bank snapshot credits one eligible donation with durable `verification = "officer"` provenance. Remote `gs-evidence` stays a witness and can still complete the three-witness quorum. Otherwise exactly three independent authenticated witness identities credit it with `verification = "witnesses"`. Officer rank is the established Guild Info threshold at admission time (`rankOrder <= effectiveThreshold`), not a payload claim. Rank or threshold changes do not upgrade an old witness report; a newer local snapshot while the character qualifies does. No manual donation approve/reject.
13. **#411 catch-up:** An accepted officer-trusted row propagates through ordinary `gs-ledger-event` gossip, including A → B → C while A is offline. The receiver accepts it only from an authenticated same-guild sender, with matching dataset/campaign/occurrence, an explicit `verifierGuid` equal to `writer`, and, when the receiver is live, the authenticated canonical cutover marker. A matching unverified candidate does not block that later row. Admission reconciles the matching pending cluster and candidates and leaves ambiguous or distinct deposits alone. A staged peer may retain a marked accepted row before cutover is installed; installing that same marker classifies it. If a staged peer retained the same occurrence unmarked or with competing authenticated markers, a later complete officer-history marked duplicate retains up to one bounded alternate without last-writer-wins; the established cutover selects the canonical marker and credits exactly once (marker arrival before or after install). Witness-only, incomplete, missing-marker, or divergent-marker officer duplicates cannot attach cutover provenance and must not create competing-ID txn aliases that redirect valuation state; competing-ID alias side effects reuse the same non-mutating officer-history preflight as catch-up credit (live canonical marker + eligibility). Missing or divergent markers alone are not promoted into live credit. Missing verifier provenance is not synthesized on catch-up or adoption. Three-witness ledger rows stay unverified candidates until local quorum. Dataset adoption replays stored `gs-evidence` as witness votes only; it does not officer-credit that replay. The accepted ledger row carries the credit. **v1 limit:** addon messages are not cryptographic proof that the named officer saw Blizzard's bank log. A guild member who can send a well-formed officer-provenance row is indistinguishable from a peer relaying accepted history. Do not treat a bare `verification` / `writer` / `rankOrder` / `isAdmin` claim as authority, and do not require the original officer to stay online.
14. **3A:** Independently initialized dataset IDs never silently merge; explicit adoption replaces.
15. **#397 / provider schema:** Valuation-aware Guild Supplies gossip uses `GS.PROVIDER_SCHEMA = 2`. Pre-#397 clients at schema 1 are incompatible under Guild Gossip's strict schema equality and must update before Guild Supplies sync/adoption resumes. Local persisted `GS.SCHEMA_VERSION` is not bumped for this wire gate.
16. **#424 campaign names:** Optional `campaignNames[campaignId]` projection keyed by immutable campaign ID. `rename-campaign` ops travel as ordinary `gs-op` bodies on provider schema 2 (no schema bump — older schema-2 peers reject the unknown kind locally without gating unrelated accounting sync). Concurrent renames/clears use last-write-wins on `(timestamp, op.id)` and must not open Troubleshooting conflicts. Target may be current or archived; authorship `campaignId` stays the prepare-time current campaign. Absent name metadata falls back to displaying the campaign ID.
17. **#397:** One effective DBMarket snapshot per canonical production donation. Earliest `(assignedAt, assignmentId)` wins, including when both an alias and its canonical id already have pending or accepted candidates. A priceable admit merges matching held pending candidates with the existing winner and the incoming body before clearing those pending keys; rejected `id_conflict` / `assignment_bound` admits must not mutate accepted or pending authority. After pending clear under the same canonical key, the accepted winner and bounded `seen` losers are rebound in the ephemeral assignment-id cache. Local assignment ids use the canonical `gsv1:<24 hex nonce>:<8 hex seq in 1..0xfffffffe>` shape so malformed or oversized suffixes cannot exhaust `valuations.nextSeq`. `BeginDatasetAdoption` cancels Logs valuation catch-up (and Start/Process refuse work while adoption is in progress) so async replacement cannot silently discard post-begin old-dataset mints. Deferred cold-index Gossip valuation drains reauthenticate `opts.sender` through `AuthenticateTransportSender` / `SenderHasEditorAuthority` each tick and fail closed on demotion, removal, identity change, or missing roster proof. Local mint requires current officer edit plus an exact guild-home realm match, and runs for a new officer direct credit and for a three-witness credit. Ingress accepts an immutable assignment only from a current editor on the authenticated transport sender; claimed actor fields are not authority. The provider record id `gs:val:<canonicalTxnId>` is the cross-client donation binding: ordinary Gossip and adoption replay validate that id against guild/dataset scope and the matching canonical donation (item id + quantity) before accepting, without rewriting the immutable `assignment.txnId` / `assignmentId`. When the bound valuation arrives before the canonical ledger donation, it is retained unpublished under `pending[canonical]` so a later authenticated matching donation can promote it without the source's local-only alias registry. One logical `assignmentId` binds to at most one canonical donation across accepted and pending buckets (including bounded loser ids); a second distinct `gs:val:` binding for the same id is rejected as `assignment_bound`, while same-donation alias convergence and `pending[A]`→`pending[C]` folding remain allowed. A rejected conflicting fold must not move `pending[A]` or patch bindings. Donation lookup during valuation admission uses an ephemeral incremental txn→event index shared by Gossip and adoption, not a per-admit full ledger scan. Cold builds and large append tails advance at most `GS.DONATION_EVENT_INDEX_BUDGET` (512) row visits per callback: adoption warms inside `ReplayAdoptionSlice` and retries `pending/awaiting_index`; Logs catch-up warms inside each `After(0)` slice before discover/price; ordinary Gossip may spend one budgeted warm inside the admit callback then locally defer the remainder on `C_Timer.After(0)` without requiring sender redelivery. Each deferred drain tick attempts at most `GS.DEFERRED_VALUATION_ADMIT_BUDGET` (defaults to `MAX_ADMISSION_WORK_PER_SLICE` / 32) queued admissions and keeps the unprocessed tail. Local reconcile prefers a just-admitted donation event or the ephemeral index (one budgeted warm); it never falls back to a full ledger scan, and an incomplete index is not treated as a definitive miss. After explicit adoption, `valuations.nextSeq` advances past retained same-nonce winner/pending/loser ids so the surviving `localWriter.nonce` cannot reissue imported assignment ids. Conflicting or unsupported bindings fail closed. Accepting officer-trusted history reconciles valuations that arrived first and, on an eligible same-realm officer, attempts a price without opening Logs. Ordinary members cannot mint. Missing TSM stays unpriced, including zero as a real price. The snapshot is the only TSM value copied into SavedVariables. Adoption advertises and pins the valuation count with the dataset descriptor; once pinned, a replacement descriptor may not omit or change that count (`source_changed`). A changed `gs-valuation` body for an already-buffered provider record id also aborts adoption as `source_changed` so a superseded provisional price cannot commit; identical redelivery stays `duplicate`. Final adoption completeness requires each buffered `gs:val:<canonical>` to match the accepted `temp.valuations.byTxn[canonical]` winner (immutable assignment fields), so a skipped or `assignment_bound` binding cannot satisfy another record's count. Replay dedupes by provider record id plus assignment identity. Malformed `gs-valuation` bodies (non-table assignment) are rejected before buffering/counting. During one completed bank-log snapshot admission, DBMarket reads may reuse a runtime-only per price-query-key cache (including zero and nil misses) cleared at outermost End; ordinary non-batch mint and Logs catch-up stay uncached across that scope. Publishing or removing a winner updates that advertised count in place, without a full export rebuild; tracked-manifest removal must not require the `gs:val` body to exist in the paced export index yet. A same-dataset staged peer keeps an authorized matching assignment pending until the installed cutover classifies that donation; it is not an accepted price or an export before then. A live uncredited row that can still receive late authenticated canonical-marker provenance also keeps that pending price until credit settles; a false→true credit transition reconciles the original immutable assignment and may attempt a local price only if still unpriced. A temporarily divergent cutover marker on a post-floor row is not automatic final rejection—bounded unpublished pending remains until credit is truly settled or the row is permanently ineligible. Permanently ineligible rows (pre-cutover floor, definitively incompatible marker provenance, malformed) discard pending. Aliasing transaction ids before that donation exists, or while its credit is still unresolved, keeps the earliest valid pending candidate under the canonical lookup key without rewriting the assignment's original transaction id, and still does not export it. An unchanged valuation store is not fully rescanned on every read; a replaced or malformed store still fails closed. Export maintenance reuses the tracked valuation manifest until the winner set or dataset changes. Valuation cleanup on a temporary adoption record does not edit the active dataset's exports. During `BeginLocalDurableNotifyBatch` (completed bank-log snapshot), accepted valuation storage and `gs:val:` / descriptor updates stay immediate while `NotifyProviderChanged` / `NotifyUI` coalesce until End; independent non-batch mints notify immediately. An unexpected TSM adapter exception is debug-logged and leaves the row unpriced. Logs-open catch-up may use bounded one-shot `C_Timer.After(0)` slices (32 discover / 8 price / reuse / cancel / idle) as a narrow #397 exception to the general no-timer TSM rule — not recurring polling. Fresh-client adoption replay may pass `allowBootstrapInstall` for valuation admits only while the live guild slot is absent; ordinary Gossip does not. Temporary pending-capacity `rejected/full` during adoption replay is retried after donations advance; malformed/unauthorized/id_conflict stay terminal.

## Lifecycle

```
login → Initialize(empty root) → EnsureGossipProvider
explicit CreateStagedRecord → staged record
New Campaign → empty items + immutable boundary
config ops / gossip / adoption (staged)
sample-only bank observation (editor, no admit) → fresh stamp
ActivateCanonicalDataset (editor + fresh bank sample) → active + liveCutover
  + ClassifyPreActivationAccounting (staged ledger retained, not live credit)
local bank snapshot → AdmitDirectObservation → officer direct credit OR 3 witnesses → production credit
remote gs-evidence → witness only (quorum still completes)
accepted officer row → gs-ledger-event catch-up (explicit verifierGuid; live marker required; original officer may be offline)
compatible editor peers InstallRemoteLiveCutover (no bank; editor auth required)
legacy profile writers isolated for that guild
```
